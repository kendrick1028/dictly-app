# 010 · [P1 안전성] 파괴적 삭제 안전장치 (폴더 캐스케이드 경고 + 되돌리기)

**우선순위**: 최상(데이터 손실). **난이도**: 중. **의존**: 없음. 두 부분(A 경고 / B 되돌리기)으로 나눠 진행 가능. B는 설계 확정 후.

## 문제
1. **폴더 삭제가 하위 전부를 경고 없이 영구 삭제**: `Sidebar.tsx:527` 확인 문구는 `'${f.name}' 폴더를 삭제할까요?`뿐인데, `main/db.ts:451-460` `deleteFolder`는 폴더의 **모든 강의(오디오·전사·채팅), 폴더 PDF, studio_items를 트랜잭션 일괄 삭제**한다. 같은 앱의 PDF 공용삭제는 "폴더의 모든 노트에서 사라집니다"라고 경고하는데(`Sidebar.tsx:104`) 훨씬 큰 폴더 삭제엔 경고가 없다.
2. **되돌리기 전무**: `Toast.tsx:100`·`lib/toastStore.ts:70`이 `onUndoAction`을 지원하나 렌더러 전체 사용처 0. 모든 삭제가 하드 삭제.
3. Home 일정·할일 삭제는 확인조차 없이 즉시(`Home.tsx:237,316`). 폴더 삭제 버튼만 hover-red 위험강조 없음(`Sidebar.tsx:528`).

## A. 캐스케이드 경고 (먼저, 저위험)
- 폴더 삭제 확인 문구에 **포함 개수**를 넣는다. 개수는 렌더러에 이미 있는 데이터로 계산하거나(폴더의 memos/pdf 수) 필요 시 main에 카운트 조회를 추가. 예: `'${f.name}' 폴더를 삭제할까요? 강의 N개·PDF M개·학습자료 K개가 함께 영구 삭제됩니다.`
- 폴더 삭제 버튼에 다른 삭제와 동일한 hover-red(`Sidebar.tsx:330` 패턴) 적용.
- Home 일정/할일 삭제(`Home.tsx:237,316`)를 `requestConfirm` 경유로(또는 B의 undo로) 일관화.

## B. 되돌리기 (설계 후)
- 최소 memo/folder/note/studio 삭제에 토스트 기반 undo(수 초) 배선. 두 가지 접근 중 택1:
  - **소프트 삭제**: 삭제를 지연 실행 — 토스트 "삭제됨 · 되돌리기"가 살아있는 동안 실제 DB 삭제를 보류, 타임아웃 후 커밋. (오디오 파일 unlink도 지연)
  - **복구 스냅샷**: 즉시 삭제하되 삭제 전 레코드+파일경로를 메모리에 보관, undo 시 재삽입/복원.
- `toastStore`의 `onUndoAction`을 사용. 폴더처럼 캐스케이드가 큰 경우 소프트 삭제가 더 안전.
- **이 부분은 착수 전 짧은 설계 노트 필요**(어느 엔티티까지, 소프트 vs 스냅샷, 오디오 파일 처리) → 사용자/상위 모델 확인 후 구현.

## 건드리지 말 것
- `deleteFolder` 트랜잭션의 삭제 범위 자체(캐스케이드는 의도된 동작 — 안전장치만 추가).
- 확인 없이도 안전한 비파괴 동작.

## 수용 기준
- A: 폴더 삭제 시 개수가 명시된 경고가 뜬다. 폴더 삭제 버튼이 위험 색으로 강조된다. Home 일정/할일 삭제도 확인 또는 undo를 거친다.
- B: 강의/폴더/노트/스튜디오 삭제 후 토스트의 "되돌리기"로 복구된다(수 초 내). 복구 시 전사·오디오·첨부가 온전.

## 검증
`npm run typecheck` 통과. `npm run dev`에서 더미 폴더 생성→삭제 경고 문구/개수 확인, undo 동작 확인(복구 후 항목·오디오 재생 확인).
